# WR — Client Tracker (installable iPhone web app)

## Context
The user wants a personal app named **WR** to track clients for what looks like a custom wood/steel furniture business. Each client record holds contact details, product photos, the materials used, the payment, and delivery status. The design should be clean and modern. The user asked for a native iPhone app, but Xcode isn't installed, so they chose an **installable web app (PWA)** they can add to the iPhone home screen. Data stays **on the phone**. The code is hosted on **GitHub Pages**.

### What the user said vs. what I assumed
| Said | Assumed (correct me) |
|---|---|
| Fields: name, phone, email, product pictures, wood type, base type (wood/steel/hybrid), paid checkbox, amount USD, status (delivered/not delivered) | "Picture of the products" means **several photos** per client, taken with the camera or picked from the library |
| Data stored "on the memory" | This means on-device storage (IndexedDB) that persists across launches. It does **not** mean in-RAM data that is lost on reload |
| Extras: search & filters, totals summary, backup export/import, tap-to-call/email | Wood type is **free text** with auto-suggestions from earlier entries (no fixed list) |
| Host on GitHub Pages | New public repo `wr` on account `mahmudmaatuk-boop`. Only the code is public, never the data. Name is **required**; the other fields are optional |
| Single user, English, USD | No login, no multi-device sync |

**Success =** On the iPhone, the user adds WR to the home screen, adds a client with photos, and sees it listed with Paid and Delivered badges and running totals. They can search, filter, edit, and delete clients, call or email a client with one tap, and export a backup file and restore it. All of this works offline.

## Approach
**Plain HTML/CSS/JavaScript (ES modules), no build step and no dependencies.** GitHub Pages serves the repo root directly. Pure logic is unit-tested with Node's built-in `node --test`.
*Why not React/Vite:* the app has four screens and one data type. A framework would add a build pipeline, a deploy workflow, and dependency upkeep, and give nothing the user can see.

### Storage
- **IndexedDB** database `wr`, with two object stores:
  - `clients`: `{ id, name, phone, email, photoIds[], woodType, baseType: 'wood'|'steel'|'hybrid', paid: bool, amountCents: int, status: 'delivered'|'not_delivered', createdAt, updatedAt }`
  - `photos`: `{ id, clientId, blob, width, height, createdAt }`. Photos are kept as Blobs, separate from client records, so the list loads fast.
- Amounts are stored as **integer cents** so floating-point rounding can't creep in. They are shown with `Intl.NumberFormat('en-US', {style:'currency', currency:'USD'})`.
- Photos are **downscaled before saving** (longest side 1600px, JPEG quality 0.82, using canvas), plus a 400px thumbnail for the list. This keeps storage small; raw iPhone photos are 3–5 MB each.
- The app calls `navigator.storage.persist()` on first launch, so the browser is less likely to clear the data.
- iOS caveat, shown in Settings: data stored by the home-screen app is separate from data in Safari tabs, and deleting the app deletes its data. That's why the backup export exists.

### Screens (hash routing: `#/`, `#/new`, `#/c/:id`, `#/c/:id/edit`, `#/settings`)
1. **Home:** "WR" header with a settings icon. A two-by-two grid of summary cards: *Total*, *Paid*, *Outstanding*, *To deliver* (count). A search field (matches name, phone, email). Filter chips: All · Unpaid · Paid · Not delivered · Delivered. Client cards show a photo thumbnail, name, wood type and base type, the amount, and Paid and Status badges. A floating **+** button adds a client. When the list is empty, it shows a friendly prompt to add the first client.
2. **Add/Edit form:** full-screen, with Cancel and Save in the header. Fields: Name*, Phone (`type=tel`), Email (`type=email`), Photos (a grid with an add tile and a remove × on each photo; the input is `accept="image/*" multiple`, which offers Camera or Library on iOS), Wood type (text + `<datalist>` of earlier values), Base type (segmented Wood / Steel / Hybrid), Amount (decimal keypad, `$` prefix), Paid (toggle), Status (segmented Not delivered / Delivered). Errors appear inline next to the field.
3. **Client detail:** a swipeable photo carousel; tap a photo for full-screen view. Phone opens a `tel:` link and email opens a `mailto:` link. Fields are listed. Quick toggles for Paid and Delivered, so the user doesn't have to open the edit form. Edit and Delete buttons; Delete asks for confirmation and also removes the client's photos.
4. **Settings / Backup:** Export writes a single `WR-backup-YYYY-MM-DD.json` file with photos embedded as base64; on iOS it's saved through the share sheet or a download. Import reads a backup file, shows how many clients it contains, and merges them by `id` (a record with the same id is replaced) after the user confirms. The screen also shows storage usage (`navigator.storage.estimate()`) and the app version.

### Visual design
- Clean, modern, and iOS-native in feel. System font stack (`-apple-system`, SF Pro), a lot of white space, 16px radius cards with soft shadows, and 44px minimum tap targets.
- Palette: warm off-white background, near-black text, **walnut accent** (`#8B5A2B`-ish) as a nod to woodwork. Green for Paid and Delivered, amber for Unpaid and Not delivered. All colors are CSS custom properties, with a full **dark mode** through `prefers-color-scheme`.
- Respects the iPhone safe areas (`env(safe-area-inset-*)`) and sets `viewport-fit=cover`. The header is sticky and translucent (`backdrop-filter`).
- App icon: a "WR" monogram on a walnut background. It's written as SVG and exported to PNG at 180/192/512 px with macOS `qlmanage`/`sips`.

### PWA
`manifest.webmanifest` (name "WR", `display: standalone`, theme color, icons) plus `apple-touch-icon` and `apple-mobile-web-app-*` meta tags. `sw.js` caches the app files (cache-first, versioned cache name), so WR opens offline. Bumping the version constant refreshes the cache.

## Verification
- `npm test` (runs `node --test tests/`). All pure logic must pass.
- Add a `.claude/launch.json` entry that serves the folder with `python3 -m http.server 5173`. Then, in the built-in browser at the **mobile viewport (375×812)** in light and dark mode:
  - Add a client with every field filled. Inject a test image through `DataTransfer` on the file input. Check that the card, badges, and totals are right.
  - Edit a client, use the quick toggles for Paid and Delivered, and check that search and each filter chip narrow the list correctly.
  - Delete a client, confirm, and check that its photos are gone from IndexedDB.
  - Reload and check the data persists. Export, clear the database, import, and check everything is restored with photos.
  - Check the service worker registers, and that the app still loads with the server stopped (offline).
  - Check the console has no errors and there's no horizontal scroll at 375px.
- **Deploy** (I'll ask before each outward-facing step): create the public repo `mahmudmaatuk-boop/wr` with `gh`, push, and enable Pages from `main` root through `gh api`. Then open `https://mahmudmaatuk-boop.github.io/wr/` in the browser pane and check it loads. Relative paths throughout make the `/wr/` subpath work.
- Hand-off: steps to install it on the iPhone (Safari → Share → Add to Home Screen) and a reminder to export backups regularly.
